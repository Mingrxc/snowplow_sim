# 交互控制与实时观测需求草案

状态：已按用户确认的 A 方案实施。

当前工作模式：`reproduce/modify`

## 1. 目标

本轮目标是改善仿真调试和人工驾驶体验，同时保留论文实验的可复现性：

1. 用一个专用终端实时显示速度、位姿、当前地形和地形参数。
2. 修复键盘左转、右转时失速、不动、突然高速前进等问题。
3. 增加接近游戏式的实时键盘控制：
   - 按住按键，持续运动；
   - 松开按键，尽快停车；
   - 前进、后退、左转、右转可以组合；
   - 明确显示当前控制状态。
4. 减少不必要的终端窗口，形成固定、简单的启动路径。

这四项属于工程化调试和操作界面改进，当前没有证据表明它们是论文方法本身。固定速度测量实验仍应使用独立的自动测速脚本，不应使用人工键盘操作产生论文结果。

## 2. 当前代码证据

### 2.1 速度观测

- `gazebo_speed_test.py` 已经订阅 `/odom` 并进行有限时长统计。
- 该脚本主要在实验结束时打印均值、最大值、最小值和标准差，没有持续刷新的实时仪表盘。
- 直接使用 `ros2 topic echo /odom` 会连续打印高精度消息，不适合作为新手实时观察工具。

### 2.2 当前键盘链路

当前推荐链路为：

```text
teleop_twist_keyboard
        |
        v
    /cmd_vel_raw
        |
        v
cmd_vel_watchdog.py
        |
        v
     /cmd_vel
        |
        v
Gazebo diff-drive
```

`cmd_vel_watchdog.py` 当前默认行为：

- 输入主题：`/cmd_vel_raw`
- 输出主题：`/cmd_vel`
- 发布频率：20 Hz
- 默认超时：0.8 秒
- 在超时之前转发最近一次非零指令
- 超时后发布零速度

因此它是“延迟停车的安全桥接”，不是严格的“松手立即停车”控制器。左、右转异常可能来自输入指令残留、转向指令与前进指令叠加、差速驱动参数、速度限幅或 Gazebo 接触求解，不能在没有运行证据前直接归因于某一个原因。

### 2.3 当前地形参数

`world_generator.py` 将每种地形的以下参数写入 Gazebo SDF：

- `mu`
- `mu2`
- `kp`
- `kd`
- `min_depth`
- `max_vel`

但是当前没有专用 ROS 话题实时发布“机器人所在区域对应的地形参数”。因此后续面板必须明确标注：

```text
configured terrain parameters
```

即“当前地形配置值”，不能直接称为“物理引擎实时测得的有效摩擦因数”。

另外，当前车轮/履带接触标签中还存在独立的轮端摩擦设置。最终有效接触摩擦由 Gazebo/ODE 接触组合决定。若要显示真正的接触力或有效摩擦，需要额外的接触传感器或 Gazebo 插件；仅根据机器人位置读取 YAML/SDF 参数不能完成这一点。

## 3. 需求可行性结论

| 需求 | 可行性 | 推荐实现 |
| --- | --- | --- |
| 专用终端实时显示速度 | 可行 | 订阅 `/odom`，5-10 Hz 原位刷新 |
| 显示当前地形名称 | 可行 | 根据 `/odom` 位姿与地形区域矩形判断 |
| 显示地形 `mu` 等配置参数 | 可行 | 读取与 World 同源的 YAML 参数 |
| 显示真正有效摩擦力 | 可行但需额外插件 | Gazebo 接触传感器/世界插件 |
| 修复左右转异常 | 可行 | 先加诊断，再按证据修正指令链和驱动参数 |
| 终端内按住移动、松手停车 | 基本可行 | 自定义 raw-terminal teleop + 短超时 |
| 完全精确的物理按键释放事件 | 纯终端不可保证 | GUI 窗口或游戏手柄输入 |
| 减少终端数量 | 可行 | ROS 2 launch 统一启动非交互节点 |

## 4. 推荐架构

推荐最终只保留两个主要终端：

### 终端 1：仿真启动

一个 ROS 2 launch 入口统一启动：

- Gazebo；
- 机器人 Spawn；
- 必要的安全桥接或控制节点；
- 可选的 RViz。

该终端主要显示启动日志和错误，不再要求用户手动维护多个后台进程。

### 终端 2：操作与实时面板

一个专用交互节点同时完成：

- 键盘输入；
- `/cmd_vel` 或安全输入主题发布；
- `/odom` 订阅；
- 当前地形识别；
- 速度、角速度、位姿和指令状态显示；
- 输入超时安全停车；
- `Ctrl+C` 退出时发布零速度。

这样既保留“单独终端实时观察”，又不需要再开一个键盘终端。

### 面板建议显示内容

```text
状态: FORWARD / BACKWARD / TURN_LEFT / TURN_RIGHT / STOP
当前地形: snow
配置摩擦 mu: 0.30
配置第二摩擦 mu2: 0.60
接触刚度 kp: 80000
接触阻尼 kd: 1000

位置: x=... y=... z=...
里程计速度 vx: ... m/s
平面速度: ... m/s
角速度 wz: ... rad/s
目标速度 vx: ... m/s
目标角速度 wz: ... rad/s
最近输入年龄: ... ms
安全状态: ACTIVE / TIMEOUT / STOPPED
```

面板只原位刷新，不无限滚屏；默认显示 2-4 位小数，原始高精度数据仍交给 CSV 或 rosbag 保存。

## 5. 键盘控制方案选项

### A：推荐，终端实时控制

实现一个项目内自定义的终端遥控节点：

- 使用终端 raw mode；
- 以固定频率发布速度；
- 依赖键盘自动重复持续产生输入；
- 超过约 0.15-0.25 秒没有新输入就发布零速；
- 左右转采用明确的差速速度组合；
- 对线速度和角速度统一限幅；
- 每次循环只发布一条最终合成指令；
- 提供强制停车键，例如空格。

优点：不增加 GUI 依赖，启动简单，终端数量少。

限制：Linux 终端通常只能可靠收到按键字符，不能保证收到独立的 key-up 事件。因此“松手停车”是基于输入超时的工程近似，而不是操作系统级别的精确释放事件。

### B：真正按键释放，GUI 键盘窗口

使用 Qt、pygame 或其他 GUI 输入窗口读取 `keydown` 和 `keyup`：

- 按下时设置对应方向；
- 松开时立即清除对应方向；
- 无需依赖键盘自动重复；
- 可以显示实时状态。

优点：最接近游戏控制。

缺点：增加图形依赖和窗口焦点问题；与“尽量少开终端”目标不完全冲突，但会多一个交互窗口。

### C：游戏手柄/控制器

使用 ROS 2 `joy` 和 `teleop_twist_joy`：

- 适合长期驾驶；
- 可用死man开关；
- 物理按键和摇杆体验最好。

缺点：需要额外硬件和 Ubuntu 设备权限，不作为当前第一步。

**推荐选择：先实施 A。** 如果用户确认必须做到操作系统级别的“松手立即停止”，再实施 B 或 C。

## 6. 左右转故障的诊断顺序

不直接猜参数，按以下顺序定位：

1. 检查键盘是否只发布到 `/cmd_vel_raw`。
2. 检查 watchdog 输出的 `/cmd_vel` 是否存在残留前进分量。
3. 分别测试：
   - 纯前进；
   - 纯后退；
   - 纯左转；
   - 纯右转；
   - 前进加左转；
   - 前进加右转。
4. 对比 `/cmd_vel`、`/odom` 和左右驱动轮关节状态。
5. 检查 `wheel_separation`、`wheel_radius`、最大速度、最大扭矩和加速度限制。
6. 检查左右关节轴方向、左右轮命名和差速插件映射。
7. 最后才调整驱动参数，并记录调整前后的实验影响。

左转/右转问题修复后，必须分别验证：

- 原地左转不会持续前进；
- 原地右转不会持续前进；
- 松手后在规定超时内停车；
- 前进和转向组合不会出现异常速度跳变；
- 发布零速度后机器人不会继续运动。

## 7. 实验语义保护

为了保持论文实验可复现性：

- 实时面板只读观测，不修改地形参数；
- 人工键盘模式用于调试和展示，不作为固定速度实验的正式数据源；
- `gazebo_speed_test.py` 继续使用固定命令、固定时长、固定起点和统一 CSV 统计；
- 每个地形实验仍使用同一套起始姿态、速度命令、稳定时间和采样窗口；
- 若后续增加接触力/有效摩擦测量，必须单独标记为实验扩展，不与当前配置摩擦值混写。
