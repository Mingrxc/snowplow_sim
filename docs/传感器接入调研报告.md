## 概述

本项目涉及的传感器包括四大类：

| 传感器 | 功能 | 仿真已实现 | 真机方案 | 优先级 |
|--------|------|:----------:|----------|:------:|
| **LiDAR** | 环境感知/障碍物检测 | 是 | 思岚/速腾聚创 + ROS 2 驱动 | 高 |
| **IMU** | 姿态估计/惯性导航 | 是 | MPU9250 / ICM-20948 + serial 驱动 | 高 |
| **Odometry** | 里程计/位置推算 | 是（插件内建） | 电机编码器 + 运动学模型 | 高 |
| **GPS/RTK** | 户外绝对定位 | 可选 | u-blox ZED-F9P + ROS 2 驱动 | 中 |
| **Camera** | 视觉感知/避障 | 可选 | USB/CSI 相机 + v4l2 驱动 | 中 |

仿真侧的核心思路是：在 URDF 中为每个传感器定义一个物理 link（连杆），然后通过 `<gazebo>` 扩展标签挂载 Gazebo 原生传感器插件，插件自动将仿真数据发布到标准 ROS 2 话题。真机侧则依赖对应的 ROS 2 硬件驱动包，发布相同消息类型的话题，确保上层感知/控制算法对仿真和真机透明切换。

## 仿真侧 — Gazebo 传感器仿真接入

### 2.1 激光雷达 LiDAR

#### 工作原理

Gazebo 提供 `ray` 类型传感器，通过虚拟激光射线阵列模拟真实 LiDAR 的扫描过程。每条射线从传感器原点射出，遇障碍物返回距离值。插件 `libgazebo_ros_ray_sensor.so` 将扫描结果封装为 `sensor_msgs/LaserScan` 消息发布。

#### URDF 连杆定义

以下代码来自 `urdf_generator.py` 的 `xacro_sensors()` 函数。传感器需同时定义 `<visual>`（外观）、`<collision>`（碰撞体）和 `<inertial>`（惯量），并通过 `fixed` 类型关节固定在 `base_link` 上：

```xml
<!-- ===== 激光雷达 ===== -->
<link name="lidar_link">
  <visual>
    <origin xyz="0 0 0" rpy="0 0 0"/>
    <geometry><cylinder radius="0.05" length="0.04"/></geometry>
    <material name="yellow"/>
  </visual>
  <collision>
    <origin xyz="0 0 0" rpy="0 0 0"/>
    <geometry><cylinder radius="0.05" length="0.04"/></geometry>
  </collision>
  <inertial>
    <mass value="0.5"/>
    <inertia ixx="0.001" ixy="0" ixz="0" iyy="0.001" iyz="0" izz="0.001"/>
  </inertial>
</link>

<joint name="lidar_joint" type="fixed">
  <parent link="base_link"/>
  <child link="lidar_link"/>
  <origin xyz="0.3 0.0 0.55" rpy="0 0 0"/>
</joint>
```

**安装位置说明**：
- `x`: 0.3m（车体前方），将传感器放在车头便于前向探测
- `y`: 0.0m（车体中心线）
- `z`: 0.55m（车顶上方），车体高 0.4m，传感器在车顶之上约 0.15m

#### Gazebo 插件配置

以下代码来自 `urdf_generator.py` 的 `xacro_gazebo_plugins()` 函数：

```xml
<gazebo reference="lidar_link">
  <sensor type="ray" name="lidar_sensor">
    <pose>0 0 0 0 0 0</pose>
    <always_on>true</always_on>
    <update_rate>10</update_rate>
    <ray>
      <scan>
        <horizontal>
          <samples>1440</samples>
          <resolution>0.00436</resolution>
          <min_angle>-3.14</min_angle>
          <max_angle>3.14</max_angle>
        </horizontal>
      </scan>
      <range>
        <min>0.1</min>
        <max>20.0</max>
        <resolution>0.01</resolution>
      </range>
      <noise>
        <type>gaussian</type>
        <mean>0.0</mean>
        <stddev>0.02</stddev>
      </noise>
    </ray>
    <plugin name="lidar_plugin" filename="libgazebo_ros_ray_sensor.so">
      <ros>
        <namespace>/</namespace>
        <argument>~/out:=scan</argument>
      </ros>
      <output_type>sensor_msgs/LaserScan</output_type>
      <frame_name>lidar_link</frame_name>
    </plugin>
  </sensor>
</gazebo>
```

**关键参数说明**：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `update_rate` | 10 Hz | 扫描频率，10 Hz 模拟常见机械式 LiDAR |
| `samples` | 1440 | 每圈采样点数 = scan_range / resolution |
| `resolution` | 0.00436 rad | 角分辨率约 0.25 度 |
| `min_angle` / `max_angle` | -3.14 / 3.14 | 360 度全方位扫描 |
| `min` / `max` range | 0.1 / 20.0 m | 测距范围 |
| `stddev` noise | 0.02 m | 高斯噪声标准差，模拟真实传感器误差 |
| `frame_name` | `lidar_link` | 点云参考坐标系，用于 TF 变换 |

#### 输出话题

| 话题 | 消息类型 | 频率 |
|------|----------|:----:|
| `/scan` | `sensor_msgs/LaserScan` | 10 Hz |

### 2.2 惯性测量单元 IMU

#### 工作原理

Gazebo 的 `imu` 类型传感器直接读取仿真引擎的刚体运动状态（线加速度、角速度），叠加上用户指定的高斯噪声后封装为 `sensor_msgs/Imu` 消息。这比实际 IMU 更理想，但通过噪声参数可以模拟真实传感器特性。

#### URDF 连杆定义

```xml
<link name="imu_link">
  <visual>
    <origin xyz="0 0 0" rpy="0 0 0"/>
    <geometry><box size="0.04 0.04 0.03"/></geometry>
    <material name="white"/>
  </visual>
  <collision>
    <geometry><box size="0.04 0.04 0.03"/></geometry>
  </collision>
  <inertial>
    <mass value="0.05"/>
    <inertia ixx="0.00001" ixy="0" ixz="0" iyy="0.00001" iyz="0" izz="0.00001"/>
  </inertial>
</link>

<joint name="imu_joint" type="fixed">
  <parent link="base_link"/>
  <child link="imu_link"/>
  <origin xyz="0.0 0.0 0.3" rpy="0 0 0"/>
</joint>
```

**安装位置说明**：IMU 应安装在车体几何中心附近，减少离心力/科里奥利力对加速度测量的影响。这里 Z=0.3m 接近车体中心高度。

#### Gazebo 插件配置

```xml
<gazebo reference="imu_link">
  <gravity>true</gravity>
  <sensor type="imu" name="imu_sensor">
    <always_on>true</always_on>
    <update_rate>100</update_rate>
    <imu>
      <angular_velocity>
        <x><noise type="gaussian"><stddev>0.0001</stddev></noise></x>
        <y><noise type="gaussian"><stddev>0.0001</stddev></noise></y>
        <z><noise type="gaussian"><stddev>0.0001</stddev></noise></z>
      </angular_velocity>
      <linear_acceleration>
        <x><noise type="gaussian"><stddev>0.001</stddev></noise></x>
        <y><noise type="gaussian"><stddev>0.001</stddev></noise></y>
        <z><noise type="gaussian"><stddev>0.001</stddev></noise></z>
      </linear_acceleration>
    </imu>
    <plugin name="imu_plugin" filename="libgazebo_ros_imu_sensor.so">
      <ros>
        <namespace>/</namespace>
        <argument>~/out:=imu/data</argument>
      </ros>
    </plugin>
  </sensor>
</gazebo>
```

**关键参数说明**：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `update_rate` | 100 Hz | IMU 更新频率，100 Hz 为标准值 |
| `accel_noise` | 0.001 m/s² | 加速度计高斯噪声标准差 |
| `gyro_noise` | 0.0001 rad/s | 陀螺仪高斯噪声标准差 |
| `gravity` | true | 传感器测量值包含重力分量（模拟真实 IMU） |

#### 输出话题

| 话题 | 消息类型 | 频率 |
|------|----------|:----:|
| `/imu/data` | `sensor_msgs/Imu` | 100 Hz |

### 2.3 里程计 Odometry

#### 工作原理

里程计不通过独立的传感器插件，而是由 `libgazebo_ros_diff_drive.so` 差速驱动插件内建计算。插件在每个仿真步长中读取左右驱动轮关节角度，根据差速运动学模型推算机器人位姿变化，发布 `nav_msgs/Odometry` 消息和 `odom→base_link` 的 TF 变换。

#### 插件配置

以下代码来自 `urdf_generator.py` 的 `xacro_gazebo_plugins()` 函数：

```xml
<gazebo>
  <plugin name="skid_steer_drive" filename="libgazebo_ros_diff_drive.so">
    <ros>
      <namespace>/</namespace>
      <argument>cmd_vel:=cmd_vel</argument>
      <argument>odom:=odom</argument>
    </ros>
    <update_rate>50</update_rate>
    <left_joint>left_drive_wheel_joint</left_joint>
    <right_joint>right_drive_wheel_joint</right_joint>
    <wheel_separation>0.65</wheel_separation>
    <wheel_diameter>0.30</wheel_diameter>
    <max_wheel_torque>20</max_wheel_torque>
    <max_wheel_acceleration>5</max_wheel_acceleration>
    <publish_odom>true</publish_odom>
    <publish_odom_tf>true</publish_odom_tf>
    <publish_wheel_tf>false</publish_wheel_tf>
    <odometry_frame>odom</odometry_frame>
    <robot_base_frame>base_link</robot_base_frame>
  </plugin>
</gazebo>
```

**关键参数说明**：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `update_rate` | 50 Hz | 里程计发布频率 |
| `wheel_separation` | 0.65 m | 左右轮距，对应 YAML 中的 `track_separation` |
| `wheel_diameter` | 0.30 m | 轮径 = `track_radius * 2` |
| `publish_odom` | true | 发布里程计话题 |
| `publish_odom_tf` | true | 发布 odom→base_link 的 TF |
| `odometry_frame` | `odom` | 里程计坐标系名称 |
| `robot_base_frame` | `base_link` | 机器人基座坐标系名称 |

#### 输出话题

| 话题 | 消息类型 | 频率 |
|------|----------|:----:|
| `/odom` | `nav_msgs/Odometry` | 50 Hz |
| `/cmd_vel` | `geometry_msgs/Twist` | 订阅（输入） |
| `/tf` (odom→base_link) | `tf2_msgs/TFMessage` | 50 Hz |

#### 差速运动学模型

差速驱动插件的里程推算基于以下运动学公式：

```
线速度 v = (ω_left + ω_right) * r / 2
角速度 ω = (ω_right - ω_left) * r / B

其中:
  r = wheel_diameter / 2 (轮半径)
  B = wheel_separation (轮距)
  ω_left, ω_right = 左右轮角速度 (rad/s)
```

Gazebo 仿真中，`ω_left` 和 `ω_right` 从驱动轮关节的仿真状态直接读取，因此里程计的准确性取决于物理仿真的精度。与真机不同，仿真里程计不会累积编码器量化误差，但仍受仿真步长和积分误差影响。

### 2.4 GPS / RTK 定位

#### 工作原理

GPS 仿真在 Gazebo 中较为简化，通常不使用 Gazebo 原生传感器，而是通过自定义插件读取仿真世界中的 ground-truth 位姿，添加噪声后发布 `sensor_msgs/NavSatFix` 消息。当前项目中 GPS 为可选配置（`enabled: false`），仅预留了 URDF 连杆。

#### URDF 连杆定义

```xml
<link name="gps_link">
  <visual>
    <geometry><sphere radius="0.03"/></geometry>
    <material name="white"/>
  </visual>
  <collision>
    <geometry><sphere radius="0.03"/></geometry>
  </collision>
  <inertial>
    <mass value="0.1"/>
    <inertia ixx="0.0001" ixy="0" ixz="0" iyy="0.0001" iyz="0" izz="0.0001"/>
  </inertial>
</link>

<joint name="gps_joint" type="fixed">
  <parent link="base_link"/>
  <child link="gps_link"/>
  <origin xyz="0.0 0.0 0.6" rpy="0 0 0"/>
</joint>
```

**安装位置说明**：Z=0.6m（车顶最高处），模拟 GPS 天线通常安装在车辆最高点的做法，减少车体对信号的遮挡。

#### 待补充

由于 Gazebo Classic 无原生的 GPS 传感器类型，完整 GPS 仿真需要额外安装 `ros-humble-gazebo-ros-pkgs` 中的 GPS 插件或使用 `hector_gazebo_plugins` 提供的 GPS 插件：

```xml
<!-- 第三方 GPS 插件示例（需安装 hector_gazebo_plugins） -->
<gazebo reference="gps_link">
  <sensor type="gps" name="gps_sensor">
    <plugin name="gps_plugin" filename="libhector_gazebo_ros_gps.so">
      <alwaysOn>true</alwaysOn>
      <updateRate>4.0</updateRate>
      <bodyName>gps_link</bodyName>
      <topicName>/gps/fix</topicName>
      <frameId>gps_link</frameId>
      <velocityTopicName>/gps/fix_velocity</velocityTopicName>
      <drift>0.0001 0.0001 0.0001</drift>
      <gaussianNoise>0.5 0.5 0.5</gaussianNoise>
      <referenceLatitude>39.9042</referenceLatitude>
      <referenceLongitude>116.4074</referenceLongitude>
      <referenceAltitude>50.0</referenceAltitude>
    </plugin>
  </sensor>
</gazebo>
```

#### 输出话题（如启用）

| 话题 | 消息类型 | 频率 |
|------|----------|:----:|
| `/gps/fix` | `sensor_msgs/NavSatFix` | 4 Hz |

### 2.5 RGB 相机 Camera

#### 工作原理

Gazebo 的 `camera` 类型传感器在仿真世界中渲染虚拟相机画面，输出 `sensor_msgs/Image` 和 `sensor_msgs/CameraInfo`。渲染基于 Gazebo 内置的 OGRE 引擎，支持分辨率、FOV 和噪声配置。

#### URDF 连杆定义

```xml
<link name="camera_link">
  <visual>
    <geometry><box size="0.06 0.04 0.04"/></geometry>
    <material name="dark_grey"/>
  </visual>
  <collision>
    <geometry><box size="0.06 0.04 0.04"/></geometry>
  </collision>
  <inertial>
    <mass value="0.3"/>
    <inertia ixx="0.0001" ixy="0" ixz="0" iyy="0.0001" iyz="0" izz="0.0001"/>
  </inertial>
</link>

<joint name="camera_joint" type="fixed">
  <parent link="base_link"/>
  <child link="camera_link"/>
  <origin xyz="0.5 0.0 0.5" rpy="0 0 0"/>
</joint>
```

**安装位置说明**：X=0.5m（车头前方），Z=0.5m（车顶上方），模拟前向视觉传感器。

#### Gazebo 插件配置

```xml
<gazebo reference="camera_link">
  <sensor type="camera" name="camera_sensor">
    <update_rate>30</update_rate>
    <camera>
      <horizontal_fov>1.047</horizontal_fov>
      <image><width>1280</width><height>720</height></image>
      <clip><near>0.1</near><far>100</far></clip>
    </camera>
    <plugin name="camera_plugin" filename="libgazebo_ros_camera.so">
      <ros><namespace>/</namespace></ros>
      <frame_name>camera_link</frame_name>
    </plugin>
  </sensor>
</gazebo>
```

**关键参数说明**：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `update_rate` | 30 Hz | 相机帧率 |
| `horizontal_fov` | 1.047 rad (60°) | 水平视场角 |
| `width` / `height` | 1280 / 720 | 图像分辨率 (720p) |
| `near` / `far` clip | 0.1 / 100 m | 视锥体裁剪范围 |
| `frame_name` | `camera_link` | 相机坐标系，用于相机外参 |

#### 输出话题（如启用）

| 话题 | 消息类型 | 频率 |
|------|----------|:----:|
| `/camera/image_raw` | `sensor_msgs/Image` | 30 Hz |
| `/camera/camera_info` | `sensor_msgs/CameraInfo` | 30 Hz |

### 2.6 完整 Gazebo 插件配置汇总

当前项目中所有传感器的 Gazebo 插件均在 `urdf_generator.py` 的 `xacro_gazebo_plugins(cfg)` 函数中统一生成。该函数按以下顺序生成：

1. LiDAR 插件（`libgazebo_ros_ray_sensor.so`）
2. IMU 插件（`libgazebo_ros_imu_sensor.so`）
3. Camera 插件（`libgazebo_ros_camera.so`，可选）
4. 差速驱动插件（`libgazebo_ros_diff_drive.so`，同时输出 `/odom` 和接收 `/cmd_vel`）
5. ros2_control 插件（`libgazebo_ros2_control.so`，仅在 `control.enable_ros2_control: true` 时启用）
6. 驱动轮传动配置（`<gazebo reference>` 中的 mu1/mu2/kp/kd 表面参数）

## 真机侧 — 真实传感器驱动与接入

真机侧的目标是：每个传感器使用对应的 ROS 2 硬件驱动，发布与仿真侧**完全相同的消息类型和话题名称**，确保上层算法可以在仿真和真机之间无缝切换。

### 3.1 激光雷达 LiDAR

#### 推荐硬件

| 型号 | 类型 | 测距范围 | 扫描频率 | FOV | 价格区间 | 适用场景 |
|------|------|----------|:--------:|:---:|----------|----------|
| RPLIDAR A2M8 | 三角测距 | 0.15-12m | 10 Hz | 360° | 约 800 元 | 室内/近距离 |
| RPLIDAR S2 | TOF | 0.1-30m | 10 Hz | 360° | 约 3000 元 | 户外/中距离 |
| 速腾聚创 RS-Helios-16P | 机械式 | 0.2-150m | 10/20 Hz | 360°×30° | > 2 万元 | 高性能室外 |

**推荐选择**：对于扫雪车户外场景，推荐 RPLIDAR S2（30m 户外测距）或更高性能的 RS-Helios 系列（如需 3D 点云）。

#### ROS 2 驱动

思岚（Slamtec）RPLIDAR 系列在 ROS 2 下有官方驱动包：

```bash
# 安装 RPLIDAR ROS 2 驱动
sudo apt install ros-humble-rplidar-ros -y

# 或从源码构建（推荐以获得最新版本）
cd ~/ros2_ws/src
git clone https://github.com/Slamtec/rplidar_ros2.git
cd ~/ros2_ws
colcon build --packages-select rplidar_ros
```

**启动命令**：

```bash
# 启动 RPLIDAR S2 驱动（默认 /dev/ttyUSB0, 1000000 baud）
ros2 launch rplidar_ros rplidar_s2_launch.py serial_port:=/dev/ttyUSB0
```

**通用串口 IMU 驱动封装思路**：

```python
# 伪代码：通用串口 IMU 驱动核心逻辑
import serial
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import Imu

class SerialIMUDriver(Node):
    def __init__(self):
        super().__init__('imu_driver')
        self.publisher = self.create_publisher(Imu, '/imu/data', 10)
        self.serial = serial.Serial('/dev/ttyUSB0', 115200, timeout=0.1)
        self.timer = self.create_timer(0.01, self.read_imu)  # 100 Hz

    def read_imu(self):
        # 读取串口数据，解析加速度/角速度/磁场
        line = self.serial.readline()
        ax, ay, az, gx, gy, gz = self.parse_line(line)
        msg = Imu()
        msg.header.stamp = self.get_clock().now().to_msg()
        msg.header.frame_id = 'imu_link'
        msg.linear_acceleration.x = ax * 9.81
        msg.angular_velocity.x = gx
        # ... 填充其他字段
        self.publisher.publish(msg)
```

#### 重要注意事项

真机 IMU 接入需要注意以下事项：

1. **坐标系对齐**：确保 IMU 芯片的 X/Y/Z 轴与 ROS 坐标系一致（X 前、Y 左、Z 上）。如不一致，需在驱动中做轴映射。
2. **重力补偿**：真机 IMU 的加速度计测量包含重力分量。大部分感知算法期望接收含重力的原始测量值（仿真侧已通过 `gravity=true` 配置保证一致）。
3. **标定**：部署前必须进行静态标定，去除加速度计和陀螺仪的零偏。IMU 的偏置温度漂移在户外寒冷环境尤为关键。
4. **协方差**：真实传感器的协方差矩阵（`orientation_covariance`、`angular_velocity_covariance`、`linear_acceleration_covariance`）应通过实验测定并填入消息中，而不是使用默认零值。

### 3.3 里程计 Odometry

#### 工作原理

真机里程计通过电机编码器获取轮速，基于差速运动学模型推算位置。这是一个开环估计，随时间累积误差，通常需要与 IMU 和 GPS 进行传感器融合。

#### 硬件选择

| 方案 | 部件 | 精度 | 价格 |
|------|------|:----:|------|
| 霍尔编码器 | 直流减速电机自带编码器 | 低（数百线/转） | 约 100 元/个 |
| 光电编码器 | 增量式光电编码器 | 中（数千线/转） | 约 300 元/个 |
| 绝对式编码器 | 磁性/光学绝对编码器 | 高 | 约 1000 元/个 |

**推荐选择**：对于履带车辆，推荐使用带编码器的直流无刷电机（BLDC），或电机+光电编码器组合。

#### ROS 2 里程计发布

里程计不是独立硬件驱动，而是一个 ROS 2 计算节点。典型实现方式：

```python
# 伪代码：基于编码器的里程计节点
class EncoderOdometry(Node):
    def __init__(self):
        super().__init__('encoder_odometry')
        self.odom_pub = self.create_publisher(Odometry, '/odom', 10)
        self.tf_broadcaster = TransformBroadcaster(self)

        # 从编码器读取左右轮速度 (rad/s)
        self.left_velocity = 0.0
        self.right_velocity = 0.0

        # 差速运动学参数
        self.wheel_radius = 0.15      # 驱动轮半径 (m)
        self.wheel_separation = 0.65  # 左右轮距 (m)

        self.timer = self.create_timer(0.02, self.update_odometry)

    def update_odometry(self):
        dt = 0.02  # 50 Hz

        # 差速模型
        v = (self.right_velocity + self.left_velocity) * self.wheel_radius / 2.0
        w = (self.right_velocity - self.left_velocity) * self.wheel_radius / self.wheel_separation

        # 积分位姿
        self.x += v * cos(self.theta) * dt
        self.y += v * sin(self.theta) * dt
        self.theta += w * dt

        # 发布 Odometry 消息和 TF 变换
        ...
```

在 ROS 2 中，也可使用 `robot_localization` 包的 EKF（扩展卡尔曼滤波）融合编码器、IMU 和 GPS 的数据，输出更准确的里程计。

```bash
# 安装 robot_localization
sudo apt install ros-humble-robot-localization -y
```

#### 输出话题

| 话题 | 消息类型 | 频率 | 说明 |
|------|----------|:----:|------|
| `/odom` | `nav_msgs/Odometry` | 50 Hz | **与仿真侧完全相同** |
| `/cmd_vel` | `geometry_msgs/Twist` | — | 订阅速度指令（输入） |

#### 履带打滑补偿

真机履带在地面行驶会产生显著打滑，导致里程计误差远大于轮式车辆。补偿策略包括：

1. **运动学打滑模型**：在线估计滑移率，修正里程计推算
2. **IMU 融合**：通过 EKF 融合 IMU 角速度和加速度，抑制打滑带来的航向漂移
3. **GPS 融合**：户外场景下，RTK-GPS 提供全局位置修正
4. **视觉里程计**：通过相机估计帧间运动，提供额外的运动估计

### 关键差异总结

1. **话题/消息一致性**：所有传感器在仿真和真机侧使用相同的 ROS 2 话题名称和消息类型，这是透明切换的前提。
2. **噪声与误差**：仿真侧的噪声是理想化的高斯模型，真机侧噪声更复杂（温度漂移、量化误差、多径效应）。算法需要在仿真中通过增大噪声参数来测试鲁棒性。
3. **打滑效应**：仿真中的履带一般不模拟打滑（除非在 ODE 中设置极低的 μ 值），而真机履带打滑是主要误差来源之一。这是仿真与真机之间最大的性能差距点。
4. **时钟**：仿真使用仿真时钟 (`/clock` 话题)，真机使用系统时钟。在节点中需正确设置 `use_sim_time` 参数。
5. **TF 生成**：仿真中所有 link 的 TF 由 Gazebo 自动发布。真机侧需要运行 `robot_state_publisher`（处理 URDF）或 `static_transform_publisher`（手动发布各传感器相对位姿）。

## TF 坐标树设计

统一的 TF 树设计是仿真-真机无缝切换的关键。以下是履带扫雪机器人的完整 TF 树：

```
map (全局地图坐标系，GPS/AMCL 定位)
  └── odom (里程计原点，随机器人移动增量更新)
        └── base_footprint (地面投影点，base_link 向地面投影)
              └── base_link (车体中心/机器人基座)
                    ├── left_drive_wheel  (左驱动轮)
                    ├── right_drive_wheel (右驱动轮)
                    ├── left_idler_wheel  (左从动轮)
                    ├── right_idler_wheel (右从动轮)
                    ├── blade_base       (扫雪铲铰接座)
                    │     └── blade      (扫雪铲板)
                    ├── lidar_link       (激光雷达)
                    ├── imu_link         (惯性测量单元)
                    ├── gps_link         (GPS 天线，可选)
                    └── camera_link      (RGB 相机，可选)
```

**说明**：

- **map → odom**：由全局定位（GPS/AMCL/SLAM）提供，表示全局参考。仿真中如有 GPS 或 SLAM 模块需额外配置。
- **odom → base_footprint**：由里程计（diff_drive 插件/编码器节点）提供。仿真中 `publish_odom_tf: true` 自动发布。
- **base_footprint → base_link**：固定变换（纯 Z 轴偏移），通常由 `robot_state_publisher` 发布。
- **base_link → 各传感器**：固定变换，由 URDF 中的 `<joint type="fixed">` 定义。

**真机侧 TF 发布建议**：

```bash
# 使用 robot_state_publisher 自动发布 base_link → sensor 的 TF
ros2 run robot_state_publisher robot_state_publisher robot_description:="$(xacro robot.urdf.xacro)"

# 手动发布各静态变换（备选方案，不依赖 URDF）
ros2 run tf2_ros static_transform_publisher 0.3 0 0.55 0 0 0 base_link lidar_link
ros2 run tf2_ros static_transform_publisher 0.0 0 0.30 0 0 0 base_link imu_link
ros2 run tf2_ros static_transform_publisher 0.0 0 0.60 0 0 0 base_link gps_link
```

## 总结与建议

### 1. 仿真-真机透明切换策略

核心原则：**话题名称 + 消息类型 + TF 帧名保持一致**

```
仿真侧: Gazebo 插件 → /scan, /imu/data, /odom
真机侧: 硬件驱动节点 → /scan, /imu/data, /odom

上层算法统一订阅 → /scan, /imu/data, /odom
```

算法开发时，只需关注标准话题，不需要关心数据来自仿真还是真机。唯一的区分点是 `use_sim_time` 参数和 `/clock` 话题的可用性。

### 2. 推荐开发流程

1. **Phase 1 — 纯仿真**：在 Gazebo 中开发感知/控制算法，使用理想数据快速迭代
2. **Phase 2 — 仿真加噪**：增大传感器噪声参数（`stddev`），测试算法鲁棒性
3. **Phase 3 — 真机部署**：运行硬件驱动节点，替换仿真话题发布源，测试实物性能
4. **Phase 4 — Sim-to-Real 调优**：对比仿真和真机数据差异，调整算法参数

### 3. 当前项目的传感器实现状态

| 传感器 | URDF 连杆 | Gazebo 插件 | 真机方案 | 状态 |
|--------|:---------:|:-----------:|:--------:|:----:|
| LiDAR | 已实现 | `libgazebo_ros_ray_sensor.so` | RPLIDAR S2 / ros-humble-rplidar-ros | 已完成 |
| IMU | 已实现 | `libgazebo_ros_imu_sensor.so` | ICM-20948 + 自建驱动 | 已完成 |
| Odometry | N/A (插件内建) | `libgazebo_ros_diff_drive.so` | 编码器 + 运动学模型 | 已完成 |
| GPS | 连杆预留 | 待补充 (hector_gazebo) | u-blox ZED-F9P / ros-humble-ublox-gps | 待完成 |
| Camera | 连杆预留 | `libgazebo_ros_camera.so` | Intel RealSense D435i / ros-humble-realsense2-camera | 待完成 |

### 4. 后续工作建议

1. **GPS 仿真补充**：集成 `hector_gazebo_plugins` 或自行编写 GPS 仿真插件，实现 `/gps/fix` 话题发布
2. **传感器融合**：配置 `robot_localization` EKF，融合 `/odom` + `/imu/data` + `/gps/fix`（如有）
3. **噪声模型校准**：通过真机数据采集，校准仿真中的噪声参数（`stddev`），使仿真更逼近真实
4. **3D LiDAR 扩展**：如需三维环境感知（雪堆检测），可添加 Velodyne/Ouster 3D LiDAR 仿真
5. **多传感器时间同步**：真机侧使用 `message_filters::TimeSynchronizer` 确保多传感器数据对齐
6. **传感器故障注入**：在仿真中添加传感器失效、数据丢失、极端噪声等故障模式，测试系统的容错能力
